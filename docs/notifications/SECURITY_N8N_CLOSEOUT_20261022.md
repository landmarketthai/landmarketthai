## Incident, credential type and blast radius

The confirmed exposure was the existing **long-lived LINE Channel Access Token** displayed on the intended channel's Messaging API console page, inadvertently included in one overly broad browser tool result during the earlier identity audit. The console section identified its type; the successful real token verification bound it to channel **2012033225**, OA **ตลาดที่ดินไทย.com / @landmarketthai**. Last strict no-send identity proof was **2026-10-22T08:31:31.712Z**. The token has not been retrieved again in this audit. No new validity assertion is made after that proof.

Treat the token as compromised for release planning. Its authority is channel-wide: application code's one-group allowlist does not limit a bearer holding the token. Depending on endpoint eligibility and known recipient/message IDs, misuse could send messages as the OA and consume quota, access permitted bot/group/profile/content information, or mutate Messaging API resources such as the webhook endpoint. The read-only endpoint inspection found the expected URL earlier; this is not a forensic finding that no misuse occurred. A token does not itself confer LINE console login, Neon/GitHub/Vercel access or the channel's HMAC secret. [LINE API reference](https://developers.line.biz/en/reference/messaging-api/nojs/).

The incident exposed the token in tool output; it did not add the token to source or sanitized reports. The earlier diagnostic used a temporary current-user-only, inheritance-disabled input file, deleted before API calls; private browser variables were subsequently cleared. This audit found the private handoff directory empty and no local `.env` credential file (only `.env.local.example`). These observations do not erase the prior tool result or prove deletion from backups/service retention. Do not share the incident transcript as a credential handoff. Owner incident disposition must cover access/retention of that result as well as token invalidation.

**Channel Secret decision: do not rotate it on the evidence currently available.** The broad read was on the Messaging API tab, which exposed the access token. The Channel Secret was obtained separately through a narrowly scoped private read; it was not printed, committed or returned by the no-send preflight. Execution #70 contains original inbound bytes/header and computed HMAC evidence, not the channel-secret key. Possession of those signed bytes is not evidence of key disclosure. No actual Channel Secret exposure is established. If owner review discovers otherwise, stop and create a separate coordinated HMAC-secret plan: reissuing it invalidates the previous secret and would break receivers still using that key. Do not rotate the Crypto credential, webhook-auth token, DB/Auth keys or unrelated LINE channels as a precaution. [Signature and secret contract](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/).

### Conditional native receiver, if inbound processing remains required

Do not implement or activate it solely to complete outbound notifications. If the owner identifies an ongoing inbound requirement, propose a Node.js Next Route Handler **`POST /api/webhooks/line`** on the existing Vercel application. Add it in a separately reviewed change with a default-off server flag; do not import the experimental Preview receiver as-is. That older route logs full group IDs and reads the whole text before checking actual size; its behavior is unsuitable as this Production contract.

- Read a bounded raw byte stream (current capture cap 65,536 bytes), stopping/canceling at the cap even when Content-Length is absent or false. Require canonical, single `x-line-signature`, HMAC-SHA256 with only `LINE_CHANNEL_SECRET`, length check and constant-time comparison **before** JSON decoding. Never reserialize/normalize signed bytes. No Channel Access Token is needed in this receiver.
- Bind signed `destination` to the owner-verified bot ID. Support signed `events: []` verification probes with 200; cap/validate batches and acknowledge supported metadata events without echoing message text, user IDs, reply tokens, raw IDs, headers or credentials. Reject invalid signature/encoding/size; no bot reply/send or unsolicited CRM action.
- For capture-only operation, retain no raw message by default and avoid DB polling/wakes. Any future exact-body capture is a separate bounded privacy approval with private owner access, expiry and explicit storage/retention design; do not rely on cross-instance process memory, public logs or an export endpoint. Do not silently attach saved #70 to tests/source.
- If business processing is approved, first define event scope and data-retention rules. Persist the minimal necessary event transactionally in an isolated inbound inbox with a unique channel/`webhookEventId` key before ACK, then process asynchronously with durable retries. Handle duplicates, out-of-order delivery and unsend requirements. `after()` alone is not durable inbound acceptance. LINE redelivery is not guaranteed and is currently off; do not enable it implicitly. [Receiving webhooks](https://developers.line.biz/en/docs/messaging-api/receiving-messages/).
- Preserve Preview Authentication and all admin/auth protections. The eventual provider-facing route must be reachable by LINE without an interactive login while relying on HMAC, TLS, body limits and platform abuse controls. Do not disable project-wide protection or put a bypass secret in a webhook URL. Ensure Auth middleware/rewrites do not intercept the signed POST or alter its bytes. No global IP allowlist is a substitute for signature verification.
- Validate locally and on protected isolated Preview through existing authorized operator access with synthetic signatures first: altered/whitespace body, wrong/missing/duplicate signature, wrong bot, malformed/oversize streaming body, empty and mixed batch, duplicate/out-of-order events, no unexpected egress/logged data. Original #70 replay, if needed, stays private and needs an explicit scoped test-data authorization. A separately approved LINE webhook-test call can target a candidate endpoint without changing the registered URL, but it sends an empty verification event and cannot prove real group-event delivery. Only after approval deploy the candidate and separately approve the OA URL switch; retain the current receiver as rollback until observed acceptance. [Webhook signature contract](https://developers.line.biz/en/docs/messaging-api/verify-webhook-signature/), [webhook testing endpoint](https://developers.line.biz/en/reference/messaging-api/nojs/#test-webhook-endpoint).

## Coordinated token replacement and revocation — not executed
